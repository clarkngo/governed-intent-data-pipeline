Research notes

Governed Intent-Driven Data Engineering

This knowledge base accompanies the in-browser lab for Governed Intent-Driven Data Engineering: An Architectural Framework for AI-Assisted Data Pipelines Across the Analytics Lifecycle by Clark Jason Ngo. The prototype is not a chatbot bolted onto a warehouse. It is a control plane: natural language is compiled into a structured plan, checked against stacked guardrails, then executed only if policy allows.

Tour the lab UI

Four-layer architecture

Each compile walks the same path. Layers are separated so a helpful model cannot skip policy or rewrite the catalog.

  1. 01 · Interaction

    Intent composer

    Role is bound first. Templates and free-form prompts are captured before any SQL exists.

  2. 02 · Planning & policy

    Compiler + guardrails

    The planner emits Intent, Datasets, Identity, Risk, Transformations, and Quality checks. Four independent verdicts run: identity, injection, catalog, tools.

  3. 03 · Execution

    In-browser DuckDB

    Only allowlisted SELECT/AGGREGATE SQL runs. PII columns are stripped in the compiled query, not as a post-filter.

  4. 04 · Observability

    Audit & lineage

    Every decision is an immutable event: who asked, what was planned, which checks fired, which SQL ran, which artifact shipped.

Intent compiler

The lab uses a deterministic compiler rather than a remote LLM so GitHub Pages can run offline-after-CDN and results stay reproducible. The contract is the same one an LLM planner would have to emit:

  • Intent — analytical job type, grain, cadence, privacy constraint.
  • Target datasets — named catalog objects, not “all tables.”
  • Identity — role, least-privilege flag, permitted actions.
  • Risk — low / medium / high / critical.
  • Transformation logic — joins, aggregations, PII stripping.
  • Quality checks — predicates that must hold before publish.

Programs the compiler can emit: retention_by_region, sla_by_region, clarify_scope, blocked_pii_export, blocked_injection. Hostile prompts never become COPY/EXPORT SQL.

Defense-in-depth guardrails

Each check returns pass, fail, or clarify. SQL is dispatched only on an overall allow.

GuardrailAsksTypical fail
Identity / RBACDoes this role have SELECT/AGGREGATE, and is PII in scope?Analyst requesting raw identifiers
Prompt injectionDoes the text try to mutate policy?“Ignore previous policies / bypass guardrails”
CatalogAre requested columns classified for this job?Projecting ssn or unbounded scans
Tools & quotasIs the tool allowlisted, and is the session under quota?Raw CSV export, COPY TO, DDL/DML, HTTP

Catalog & classification

Classification is the source of truth. A join key is not a license to project PII from the same table.

ClassExamplesRule
join_keycustomer_idUsable in JOIN / GROUP BY only
internalregion, plan, mrr, csatApproved analytics projections
piiname, emailBlocked for Analyst; HITL may still not dump them
restrictedssnNever projected, never overridable

Approved fact tables: subscriptions, support_tickets. customers is mixed — join for region only.

Roles

  • Analyst — least privilege. SELECT + AGGREGATE. Cannot approve HITL. PII exports block and may only escalate.
  • Admin / Data Engineer — same SQL tools, plus APPROVE_HITL. Break-glass runs a substitute governed aggregate. It does not replay the blocked prompt and still strips SSN.

Human-in-the-loop

HITL is a gate, not an override-everything switch. Analysts escalate with a written justification. Admins may approve. The control plane then compiles the approved retention program — not the original dump or jailbreak. Restricted columns remain non-overridable even under break-glass. That is the difference between “the model was helpful” and “the platform stayed governed.”

Execution sandbox

DuckDB-Wasm (1.29.0) loads mock customers, subscriptions, and support_tickets entirely in the tab. Identifiers are synthetic (@example.invalid, 000-00-1xxx). If Wasm workers fail, an equivalent JavaScript engine runs the same aggregations so the demo still completes. No GPU, no warehouse credential, no outbound data plane.

Quality gates & artifacts

After SQL returns, the lab checks row count, quota, absence of PII column names, retention in 0–100, CSAT in 1–5, and region completeness. Only then is a JSON/CSV artifact minted. A quality failure is a publish block, even if guardrails had allowed the session.

Audit & lineage

The console stores timestamp, role, decision (allow, block, clarify, escalated, allow_hitl), guardrail vector, SQL, quality summary, and artifact link. A short session history is kept in localStorage key gidp-lab-v1.

Threat model (what the lab demonstrates)

  • Prompt injection — policy-mutating text must not compile into executable SQL.
  • Confused deputy — the planner must not inherit Admin powers because the prose sounds urgent.
  • Classification bypass — joining customers for region must not leak email/ssn.
  • Tool abuse — raw export / COPY / DDL are denied even if SELECT would have been allowed.
  • Unbounded exploration — “show everything” is a clarify, not SELECT *.

Glossary

GIDP
Governed Intent-Driven Data Engineering — the control-plane pattern this lab simulates.
HITL
Human-in-the-loop review. Authorization to run a safer substitute job, not to honor a blocked dump.
Break-glass
Admin-only path with justification. Restricted class remains non-overridable.
Clarify
Planning halt: the intent is too vague to authorize a warehouse session.
